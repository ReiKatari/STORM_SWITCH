## 2. Стандарт оформления релизов GitHub (Release Body Guidelines)
При создании или обновлении релизов GitHub (`PATCH` / `POST` к GitHub Releases API) строго соблюдать следующую структуру:

### Правило 1: Запрет дублирования заголовка и префикса 'v'
- **Никогда не добавлять заголовок первого уровня `# H1` с названием проекта и версией в начало описания релиза**, так как GitHub отображает название и версию в заголовке страницы релиза автоматически.
- **Никогда не указывать букву `v` перед номером версии** (писать `4.8.8`, `Релиз 4.8.8`, а не `v4.8.8` или `Релиз v4.8.8`).

### Правило 2: Запрет подписей автора в релизах
- **Запрещено добавлять фразы вида `Собрано и опубликовано автором...` в конце или теле релиза**.

### Правило 3: Структура описания релиза
```markdown
> 💡 **Релиз {version}** — *{Краткое описание назначения утилиты/проекта}*

---

### 🚀 Ключевые изменения и улучшения
- 🌟 **[Компонент / Функция]**: [Описание ключевого изменения]
- 🌟 **[Компонент / Функция]**: [Описание ключевого изменения]

<details>
<summary><b>📋 Полный список изменений (нажмите, чтобы развернуть)</b></summary>

- 🔹 **[Пункт 1]**: [Детальное описание]
- 🔹 **[Пункт 2]**: [Детальное описание]

</details>

<details>

<details>
```

- Вокруг тегов `<summary>` и `</details>` обязательно оставлять пустые строки (двойной перенос строки), чтобы таблицы, списки и вложенный Markdown рендерились GitHub без сбоев разметки.
- Не разбивать существующие Markdown-таблицы и блоки кода на плоские списки.

## 4. Стандарты архитектуры приложений, инсталляторов, иконок и запуска

### Правило 1: Единственный экземпляр приложения (Single Instance Mode)
- **Программа может запускаться только в одном экземпляре**:
  - Использовать системный `Mutex` (например, `Global\STORM_<PROJECT_NAME>_SingleInstanceMutex`) или `EventWaitHandle` для контроля уникальности процесса.
  - При попытке повторного запуска: существующее главное окно активируется и выводится на передний план (`SetForegroundWindow` / `Activate`), а пользователю отображается стилизованное под активную тему уведомление / сообщение о том, что экземпляр программы уже запущен.

### Правило 2: Собственная уникальная иконка (Эталон: `E:\STORM GAME SYSTEM`)
- **Каждой программе генерируется СОБСТВЕННАЯ уникальная иконка в едином стиле экосистемы STORM SOFT**:
  - Иконка генерируется в ультра-высоком качестве и компилируется в мультислойный `AppIcon.ico` (набор разрешений: 256x256, 128x128, 64x64, 48x48, 32x32, 16x16) через инструмент конвертации `IcoTool`.
  - Иконка внедряется во все компоненты приложения: свойства проекта `.csproj` (`<ApplicationIcon>AppIcon.ico</ApplicationIcon>`), окна WPF / UI (`Icon="Assets/AppIcon.ico"`), инсталлятор `StormInstaller`, манифест `app.manifest` и панель задач Windows.

### Правило 3: Стандарт каталога установки инсталлятора (Setup Directory)
- **Установка строго в папку с названием программы БЕЗ указания версии**:
  - Целевой каталог установки инсталлятора `StormInstaller` / Setup должен формироваться **исключительно по названию программы** без добавления номера версии, даты или суффиксов.
  - *Пример правильного пути:* `%LOCALAPPDATA%\Programs\STORM YANDEX MUSIC DOWNLOADER` или `%ProgramFiles%\STORM YANDEX MUSIC DOWNLOADER`.
  - *Пример ошибочного пути:* `STORM YANDEX MUSIC DOWNLOADER 1.0.1`, `STORM YANDEX MUSIC DOWNLOADER v1.0.1`.
  - Это обеспечивает бесшовное обновление поверх существующей версии, гарантирует сохранность путей к исполняемым файлам, ярлыкам меню «Пуск» и записям реестра.

### Правило 4: Стандарт отображения логотипов и поведения кнопок инсталлятора (StormInstaller UI and Lifecycle)
- **Размещение иконки программы и фирменного логотипа**:
  - **Иконка программы в шапке**: в верхнем правом углу шапки инсталлятора (Header) отображается иконка самой устанавливаемой программы — **чисто, БЕЗ огранки, рамок, контейнеров и фоновых выделений**.
  - **Фирменный красно-черный логотип STORM SOFT**: располагается **ниже горизонтального разделителя шапки** в основном теле (Body), справа от блока выбора типа установки программы. Выравнивается **строго под иконкой программы в шапке и имеет точно такой же размер**, также отображается **чисто, БЕЗ огранки, рамок и выделений**.
- **Логика работы кнопок и завершения установки**:
  - **Старт процесса установки**: при нажатии кнопки «Установить» она немедленно блокируется (`Enabled = false`), а кнопка «Отмена» **остаётся активной** (`Enabled = true`), позволяя пользователю прервать операцию.
  - **Завершение процесса установки (100%)**: по достижении 100% прогресса обе кнопки («Установить» и «Отмена») блокируются (`Enabled = false`), и инсталлятор автоматически закрывается, при необходимости запуская установленное приложение.

## 5. Стандарты интерфейса (UI/UX), типографики и элементов управления

### Правило 1: Типографика, союзы и регистр (Sentence Case)
- **Строгий запрет символа `&` вместо союза «и»**:
  - Всегда писать союз «и» словом (в русском языке) или «and» (в английском). Запрещено использовать `&` в заголовках, пунктах меню, кнопках, вкладках, названиях разделов, карточках и документации.
- **Регистр текста (Sentence case)**:
  - В названиях разделов, вкладок, кнопок, подсказок, списков и настроек с заглавной буквы пишется **только первое слово** (за исключением аббревиатур и имен собственных).
  - Запрещён англоязычный Title Case (когда каждое слово пишется с заглавной буквы).
  - *Пример правильного написания:* `Галерея и история`, `Настройки и обновления`, `Службы и процессы`, `Диски и SMART накопители`.
  - *Пример ошибочного написания:* `Галерея & История`, `Галерея И История`, `Настройки & Обновления`.

### Правило 2: Единый формат даты и времени
- **Дата**: строго в формате `dd.MM.yyyy` (например: `01.09.2026`).
- **Время**: строго в 24-часовом формате `hh:mm` / `HH:mm` (например: `15:30`, `09:05`).

### Правило 3: Единая система визуальных тем оформления
- Во всех проектах с графическим интерфейсом должна поддерживаться единая стандартизированная палитра и логика тем оформления (8 эталонных стилей):
  1. **STORM DARK** — Тёмный кибер (основной тёмный фон, сланцевые тона, акцент Cyan `#00D2FF`).
  2. **STORM NIGHT** — Чёрный OLED (глубокий чёрный фон `#0A0B10`, чистый неоновый акцент `#00F0FF`).
  3. **STORM DAY** — Светлая тема (контрастный чистый светлый фон, акцент `#0284C7`).
  4. **STORM MIDNIGHT** — Аметистовая ночь (тёмно-фиолетовый фон `#15112B`, фиолетовый акцент `#A855F7`).
  5. **STORM MATRIX** — Матричный зелёный (кибер-зелёный неоновый акцент `#00FF66` на тёмно-изумрудном фоне).
  6. **STORM CYBERPUNK** — Неон Найт-Сити (ярко-розовый неоновый акцент `#FF007F` на ультрафиолетовом фоне).
  7. **STORM FANTASY** — Королевское золото (благородный золотой акцент `#F59E0B` на глубоком ночном фоне).
  8. **STORM WARHAMMER 40K** — Имперская готика (готическое золото `#D4AF37` на тёмно-титановом фоне).
- **Единая логика выбора и управления**:
  - Карточки выбора тем с цветовым маркером-индикатором, названием темы и описанием палитры.
  - Мгновенное динамическое переключение на лету через ResourceDictionary / ThemeManager без перезапуска программы.
  - Автоматическое сохранение выбранной темы в `%APPDATA%/<ProjectName>/settings.json` и применение при старте.

### Правило 4: Объёмное 3D-оформление элементов интерфейса (Эталон: `E:\STORM SYSTEM OPTIMIZER`)
- Все интерактивные элементы управления (кнопки, поля ввода, карточки, переключатели, чекбоксы, ползунки) должны иметь выразительный **объёмный (3D / Elevated / Volumetric)** дизайн:
  - **Кнопки (Buttons)**:
    - Мягкие реалистичные тени `DropShadowEffect` (`Direction=270`, радиус размытия `8-12px`, глубина `2-3.5px`, прозрачность `0.35-0.5`).
    - Тактильная физика нажатия (Tactile Press): плавное смещение по оси Y при наведении (`TranslateTransform Y="-1"`) и вдавливание при клике (`TranslateTransform Y="1.5"` + `Scale 0.98` с уменьшением тени).
    - Градиентные неоновые кнопки ключевых действий (`StormHeroButton` с акцентным свечением).
  - **Поля ввода (Inputs / TextBoxes)**:
    - Объёмный контур с акцентной подсветкой при фокусе, яркий цветной курсор (`CaretBrush`), полупрозрачное выделение и закругление углов (`CornerRadius="6-8"`).
  - **Чекбоксы (CheckBoxes)**:
    - **Сплошной квадрат со скруглением (`CornerRadius="4"`) с акцентной неоновой заливкой при включении и БЕЗ устаревших галочек**.
  - **Ползунки (Sliders)**:
    - Объёмный стилизованный трек с подложкой и светящийся `Thumb` с акцентным неоновым кольцом и тенью `DropShadowEffect`.
  - **Карточки и панели (Cards & Containers)**:
    - Полупрозрачный градиентный фон (`StormCardGradient`), тонкая акцентная рамка (`CardBorderBrush`) и визуальный эффект парения над основным фоном.

## 8. Стандарт оптимизации токенов и ускорения работы (Rust Token Killer - RTK)
- **Обязательное использование RTK**:
  - При выполнении команд терминала (`git`, `cargo`, `npm`, `dotnet`, `grep`, `find`, `cat`, тесты, линтеры, сборка) ВСЕГДА маршрутизировать вызовы через CLI-прокси `rtk`:
    - **Git операции**: `rtk git status`, `rtk git diff`, `rtk git log -n 10`, `rtk git add`, `rtk git commit -m "..."`, `rtk git push`, `rtk git pull`
    - **Тестирование (сокращение шума до 90%)**: `rtk cargo test`, `rtk pytest`, `rtk npm test`, `rtk vitest`, `rtk jest`, `rtk test <команда>`
    - **Поиск и инспекция файлов**: `rtk grep <паттерн>`, `rtk find <паттерн>`, `rtk read <файл>`, `rtk ls <директория>`, `rtk diff <файл1> <файл2>`
    - **Сборка и линтинг**: `rtk lint`, `rtk tsc`, `rtk err <команда>`
  - В цепочках команд префикс сохраняется для каждого шага: `rtk git add . && rtk git commit -m "feat: ..."`
  - Если для команды нет специализированного фильтра в RTK, она выполняется прозрачно как есть — префикс `rtk` всегда безопасен.
  - Повторный запуск сырой команды `rtk proxy <cmd>` допускается ТОЛЬКО если вывод оказался повреждённым или противоречит коду возврата.
  - Строго запрещено засорять контекстное окно модели длинными простынями успешных логов, прогресс-баров и мусорного вывода. Это сохраняет фокусировку рассуждений LLM и радикально снижает затраты токенов.
